For a new developer joining this project, here is a brief cheatsheet covering the essential commands, architectural rules, and testing procedures.

### 1. Core Development Commands
This project uses an **Nx monorepo** structure. All commands should be run from the project root.

* **Start API Server**: `npx nx serve api`.
* **Database Sync**: `npx nx db-push api` (Syncs Prisma schema to your local DB).
* **Database Viewer**: `npx nx db-studio api` (Opens a GUI to view data).
* **Run All Tests**: `npx nx run-many -t test`.

### 2. Testing & Environment
The testing environment is strictly separated from development to prevent data pollution.

* **Run API Tests**: `npx dotenv-cli -e .env.test -- npx nx test api --runInBand`.
    * *Note: `--runInBand` is required to prevent connection bottlenecks in WSL environments.*
* **Prisma Test Sync**: `npx nx db-push api --configuration=test`.
* **Provision API Key**: Use the internal script to generate a valid test key:
    `npx dotenv-cli -e .env.test -- npx ts-node apps/api/src/scripts/generate-key.ts`.

### 3. Core Architectural Rules (Hard Constraints)
New developers must follow these strict safety rules for the financial ledger:

* **Locking**: Always use `SELECT FOR UPDATE` (pessimistic locking) when modifying wallet balances to prevent double-spending.
* **Idempotency**: All `POST`, `PUT`, and `PATCH` requests **must** include an `Idempotency-Key` header.
* **Immutability**: The `AuditLog` table is strictly for record-keeping; do not write code that updates or deletes these logs.
* **Timeouts**: Every Prisma `$transaction` must have a 30-second timeout configuration: `{ timeout: 30000, maxWait: 30000 }`.

### 4. Manual Verification
Manual regression testing is performed using the provided Postman collection.

1.  **Import**: Import the collection from `apps/api/postman/WalletOS_API_Tests.postman_collection.json`.
2.  **Auth**: Set the `apiKey` variable in Postman using the key generated by the script mentioned above.
3.  **Flow**: Run "Create Wallet" first; scripts within the collection will automatically populate variables for subsequent transaction tests.
